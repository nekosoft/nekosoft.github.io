Method

Seven questions before making a claim

01Source

Which system produced the record? CloudTrail, application audit and runtime telemetry see different things.

02Time

Event time, ingestion time and enrichment time may differ. Correlation needs a defensible window.

03Actor

Which human, session, service role, task, node or provider grant performed the action?

04Action

Was this a request, an allowed decision, an API call, a process start or a completed result?

05Resource

Which merchant, workspace, task, file, domain or role was affected?

06Outcome

Success, allowed, HTTP 200 and accepted flow each mean something different.

07Join key

Which ID links records without relying only on close timestamps?

Good responder language: “This source establishes X. It is consistent with Y. It does not yet establish Z.”

Debrief

Evidence confidence

What the incident record can—and cannot—say

✓ Observed

  • Valid password-backed merchant session
  • GitHub Raw object downloaded and executed
  • Root-running task, Nikto scan and shadow-file access
  • Drive folder made link-readable
  • Credential submission stored and anonymously downloaded
  • Queued task started after session termination

≈ Reasonable inference

  • The retrieved helper caused the near-immediate callbacks
  • The public page was part of the attacker’s phishing objective
  • The password was stolen or reused before the first observed login

State these as hypotheses and name the supporting correlation.

? Not proven

  • Reconnaissance before login
  • Privilege escalation or host compromise
  • AWS credentials returned or used
  • Use of the stolen merchant credential elsewhere
  • Additional victim submissions
  • Production frontend compromise
Best final prompt

“Which single additional event, field or correlation would most change your confidence—and which team should own producing it next time?”
